# 微信 4.x 数据库密钥提取：技术文档调研报告

**针对环境：** Windows / 微信 **4.1.15.13**（`D:\Program Files\Tencent\Weixin`），账号 `wxid_example123456`
**调研日期：** 2026-10-15
**核心问题：** 密钥到底怎么拿到的？为什么被动内存扫描抓不到？

---

## 0. 一句话结论

> **微信 4.1.10 起（Windows，2025-05）引入了「零驻留」策略：数据库密钥派生后即用即弃，
> 稳态内存中不再存在任何可寻形态。因此"扫描内存找密钥"这条路从原理上就死了，
> 不是特征失效，而是密钥根本不在那里。只有主动介入（断点 / Hook / 注入）+ 重登录时机窗口才能拿到。**

这解释了我们实测的全部现象。

## 1. 加密算法：稳定不变（这部分我们已独立复现）

来源：[wxlocal WECHAT_4.1.13_RESEARCH.md](https://github.com/NinjaSln-labs/wxlocal/blob/main/docs/WECHAT_4.1.13_RESEARCH.md)

微信 4.x 全线使用 **SQLCipher 4**（WCDB 封装），参数自 4.0 起稳定：

| 参数 | 值 |
| --- | --- |
| 对称加密 | AES-256-CBC |
| 消息认证 | HMAC-SHA512 |
| KDF | PBKDF2-HMAC-SHA512 |
| 迭代次数 | **256,000** |
| 页大小 | 4096 |
| 保留区 | 80 字节（IV 16 + HMAC 64） |
| IV 偏移 | 4016 |
| HMAC 偏移 | 4032 |

**每页布局：**
```
[0:16]      salt（仅第 1 页；后续页复用）
[16:4016]   加密数据
[4016:4032] IV
[4032:4096] HMAC-SHA512
```

**HMAC 验证公式：**
```python
mac_salt = db_salt XOR 0x3a
mac_key  = PBKDF2-HMAC-SHA512(enc_key, mac_salt, iterations=2, dklen=32)
valid    = HMAC-SHA512(mac_key, page1[16:4032] + pack('<I', 1)) == page1[4032:4096]

enc_key  = PBKDF2-HMAC-SHA512(passphrase, db_salt, iterations=256000, dklen=32)
```

**每个 `.db` 有独立 salt，但共享同一个账号级 passphrase。**

> ✅ 这与我从 WeChatDataAnalysis 源码提取的参数**完全一致**，也与我的独立解密实现
> （[standalone_decrypt.py](standalone_decrypt.py)）一致：我用你的一把口令成功解开了 10 个
> salt 各不相同的数据库，`bad_hmac_pages=0`。

**重要不变量：**
1. 数据库加密算法和 passphrase **在版本升级时不变** —— 4.1.9 提取的 key 在 4.1.13 上依然有效（27/27 通过）
2. passphrase **与账号绑定**，不随进程重启而变
3. 同一账号 **Windows / macOS 的 key 不通用**
4. 手机端 `Backup.db` 用独立密钥，PC 工具无法解密

## 2. 密钥缓存机制的三次变迁（核心）

| 阶段 | 版本范围 | 内存中的形态 | 被动扫描 |
| --- | --- | --- | --- |
| **A：raw key 缓存** | 4.0.x ~ 4.1.9.x | `x'<64hex_enc_key><32hex_salt>'` 字符串 | ✅ 有效 |
| **B：passphrase 半驻留** | 4.1.1+ | 32 字节 passphrase 二进制，Config.Cipher 对象可扫 | ⚠️ 需 PBKDF2 派生 |
| **C：零驻留** | **4.1.10+** | enc_key 派生后即用即弃，稳态内存无任何可寻形态 | ❌ **无效** |

**关键时间节点（社区验证）：**

| 时间 | 事件 |
| --- | --- |
| 2025-05-13 | Issue #96 首次报告 Linux/macOS 4.1+ 不再缓存 raw key |
| 2025-05-24 | Windows 4.1.9.57 仍可用 `x'96hex'` 扫描，27/27 命中 |
| **2025-05-27** | **Windows 4.1.10.24 首次报告 0 候选（Issue #125）** |
| 2025 系统性验证 | 对 4.1.10.53 做 **1.3GB 内存 dump + 离线穷举**，确认 enc_key 以任何形态均不驻留 |
| 2025 下半年 | 4.1.11+ 进一步移除 `x'96hex'` 模式 |
| 4.1.12.26 | stargazer-2026 用 Frida spawn hook `Weixin.dll` MMV1 函数验证 25/25 成功 |
| 4.1.13.12 | 继承零驻留策略，被动扫描确定无效 |
| **4.1.15.13** | **你的版本 —— 仍在零驻留区间，本文档未覆盖，属"需自行逆向"** |

### 2.1 社区那份 1.3GB 验证，和我们的实测完全一致

文档记录的验证结论（4.1.10.53）：
- `x'96hex'` 模式：**0 个**
- raw key 32 字节直接搜索：**0 次**
- XOR / 翻转 / 拆半等变换：**全无**
- salt 邻域指针解引用：**无**

我在你的 4.1.15.13 上做的（[raw_mem_search.py](raw_mem_search.py)、[hunt_key_encodings.py](hunt_key_encodings.py)、[hunt_all_memory.py](hunt_all_memory.py)）：

| 我扫描的 | 量 | 结果 |
| --- | --- | --- |
| 内存类型 | IMAGE 541 MB + MAPPED 110 MB + PRIVATE 220 MB = **869 MB** | — |
| 编码 | raw32 / 倒序 / UTF-16LE / UTF-16BE / hex小写 / hex大写 / base64 / 带空格hex | **全部 absent** |
| 进程 | Weixin.exe + wechatdb_broker.exe | **全部 absent** |

**→ 独立复现了文档的结论。我们不是操作失误，是原理上不可能。**

## 3. 密钥提取方法全景（8 种）

### 3.1 失效的方法（别浪费时间）

| 方法 | 原理 | 状态 |
| --- | --- | --- |
| **一：被动内存扫描 `x'96hex'`** | 扫 `Weixin.exe` 匹配 `x'<64hex_key><32hex_salt>'` + HMAC 校验 | ❌ **4.1.10+ 无效** |
| **二：Config.Cipher 对象扫描** | 定位 `com.Tencent.WCDB.Config.Cipher` 附近的 WCDB 配置对象 + PBKDF2 | ⚠️ 4.1.10+ 大概率无效；4.1.1~4.1.9 可能有效。但见 §4 重要更新 |
| **五：key_info.db** | `all_users\login\<account>\key_info.db` 的 `LoginKeyInfoTable` | ❌ **不是明文**，是加密包装。滑动窗口扫 32/48 字节块 + 多种 PBKDF2 组合，**均无法通过 HMAC** |

失效的工具列表：wechat-decrypt、chatlog（内置扫描）、wx-cli、L1en2407/wechat-decrypt

### 3.2 有效的方法（按推荐度排序）

#### ★ 方法六：降级提取 + 升级（**最安全、最可靠、零注入风险**）

**原理：** passphrase 跨版本有效且与账号绑定。所以去装一个 **≤4.1.9** 的老版本微信登录同一账号，
用老版本仍有效的内存扫描拿密钥，再回到新版本用。

```
1. 备份整个 xwechat_files 目录
2. 在 VM 或备用目录安装微信 4.1.9.x
3. 登录同一账号
4. 运行 find_all_keys.py / wcdb-key-tool / wx_key 提取密钥
5. 保存 64 位 hex passphrase
6. 恢复使用 4.1.15.13
7. 用保存的 passphrase 正常解密（跨版本有效，已验证 27/27）
8. 屏蔽自动更新：
   Add-Content C:\Windows\System32\drivers\etc\hosts "`n127.0.0.1 dldir1.qq.com`n127.0.0.1 dldir1v6.qq.com"
```

难度 ★★☆ / 风险**无** / 成功率**确定**

老版本存档：[cscnk52/wechat-windows-versions](https://github.com/cscnk52/wechat-windows-versions)、
[iibob/WechatWindowsVersionHistory](https://github.com/iibob/WechatWindowsVersionHistory)

#### ★ 方法七：重新登录时机窗口（**你的猜想，文档证实存在，但有前提**）

**原理：** passphrase 在登录/数据库初始化时**短暂出现在寄存器或栈上**。

```
1. 微信设置 → 退出登录（不是关窗口，是退出账号）
2. 确认 Weixin.exe 全部退出（任务管理器检查）
3. 以管理员启动提取工具（断点或扫描）
4. 启动/登录微信
5. 登录完成后 5~30 秒内，数据库逐个打开，断点会多次命中
6. 同一个 passphrase 适用于所有 DB（只需捕获一次）
```

**关键前提（文档原话）：**
> 对于 4.1.10+ 零驻留版本，「重新登录 + 被动扫描」**仍然无效**，必须配合**断点/Hook**。

**→ 你的直觉是对的：登录时机确实是唯一的明文窗口。但那个窗口极短（寄存器/栈上），
被动轮询扫描（我们那套 7 秒一轮）根本追不上，必须用调试器断点或 Hook 精确截获。**

`wcdb-key-tool` 说明：首次提取需要"退出登录再重新登录"以触发密钥重新计算。
`chatlog` FAQ：完全退出 PC 微信重新登录（PID 不同）后手动执行可正常获取。

#### 方法三：调试器断点（x64dbg / WinDbg）

**原理：** 在 `Weixin.dll` 里定位 WCDB `setCipherKey` / codec 配置函数，数据库打开时断点截获 passphrase。

已知偏移（**版本相关，不可直接复用**）：

| 版本 | 定位线索 | RVA |
| --- | --- | --- |
| 4.1.1.19 | `com.Tencent.WCDB.Config.Cipher` xref | `0x4AEA40` |
| 4.1.12.26 | `MMV1` 字符串 xref | `0x3486140` |
| 4.1.13.12 / **你的 4.1.15.13** | **需自行逆向** | 未知 |

```
1. 完全退出微信
2. x64dbg → File → Open → Weixin.exe（或 Attach 后重新登录）
3. 在 Weixin.dll+RVA 设软件断点
4. 运行，扫码/密码登录
5. 断点命中：
   - 4.1.1.x ：看 RDX → [RDX+8] 指向 32 字节 passphrase
   - 4.1.12.x+：看 RCX → 结构体前 32 字节 = passphrase
6. 记录 64 位 hex，立即保存
```

难度 ★★★★★ / 风险中 / 成功率高。注意每次小版本更新 RVA 几乎必变。

#### 方法四：Frida Hook（spawn 模式）

**原理：** 进程启动最早期注入，hook codec 配置函数入口，`onEnter` 中读 RCX 指向结构的 password 字段。

```python
import frida, sys
WEIXIN = r"D:\Program Files\Tencent\Weixin\Weixin.exe"
HOOK_OFFSET = 0x3486140   # ⚠️ 仅 4.1.12.26；4.1.13+ 需重新定位
pid = frida.spawn(WEIXIN)
session = frida.attach(pid)
script = session.create_script(f"""
var base = Process.getModuleByName('Weixin.dll').base;
Interceptor.attach(base.add({HOOK_OFFSET}), {{
    onEnter: function(args) {{
        var pw = Memory.readByteArray(args[0], 32);
        send({{type:'password', data: pw}});
    }}
}});
""")
def on_message(msg, data):
    if msg['type'] == 'send':
        print('PASSPHRASE:', data.hex() if data else msg['payload'])
script.on('message', on_message)
script.load()
frida.resume(pid)
sys.stdin.read()
```

**关键限制：**
- 必须 **spawn**（启动时注入）；attach 已运行进程会**错过**密钥设置时机 —— 这正是我们失败的另一种解释
- 有 anti-hook 检测，可能崩溃或弹错误报告
- **有封号风险**

难度 ★★★★ / 风险中高

#### 方法八：wx_key GUI（DLL 注入）

**项目：** [ycccccccy/wx_key](https://github.com/ycccccccy/wx_key)（活跃 fork：[bubuqing99/wx_key](https://github.com/bubuqing99/wx_key)）

原理：`wx_key.dll` 注入 `Weixin.exe`，hook 密钥设置函数，GUI 一键获取。

```
1. 下载 wx_key Release (app.zip)
2. 解压到纯英文路径（中文路径会导致 DLL 加载失败）
3. 先登录微信
4. 运行 wx_key.exe → 获取数据库密钥
5. 复制 64 位 hex（注意：不是 8 字符显示格式）
```

状态：⚠️ 声称支持所有 4.x，**实测版本至 4.1.5.11**；4.1.13+ 需自行测试。
社区反馈：Windows 4.1.x 用户用 wx_key 手动获取后粘贴到 chatlog 可正常解密。

难度 ★☆☆ / 风险中 / 成功率中高

## 5. 风险提示（务必看）

来源：文档 §7

### 5.1 封号与法律风险

| 风险 | 级别 | 说明 |
| --- | --- | --- |
| **DLL / Frida 注入** | **中高** | 腾讯可检测注入行为，**有真实封号案例**（Issue #128, #140） |
| 被动内存读取 | **低** | `ReadProcessMemory` 不涉及代码注入，相对安全 |
| 调试器附加 | 中 | x64dbg 附加可能被检测 |
| **律师函** | **高** | **多款工具作者收到腾讯律师函后删库（2025-10）** |
| 数据隐私 | — | 仅限读取自己的数据；他人聊天记录涉及法律问题 |
| 服务条款 | — | 违反微信用户协议，账号可能被限制 |

**文档明确建议：**
- 主号 / 工作号**避免注入类方案**
- **优先使用降级提取（方法六）或被动方案**
- 提取后立即断开调试器 / 卸载 Hook
- passphrase **等同于账号密码**，妥善保管

### 5.2 工具生态风险
- 多个 wechat-decrypt fork 已停止维护或收到 DMCA
- GitHub 上部分仓库已被删除（**451 Unavailable For Legal Reasons**）—— 我在调研时
  访问 `0xlane/wechat-dump-rs` 就返回了 **HTTP 451**，正对应此条
- 微信更新频繁（约每 1~2 周一个小版本），工具滞后严重

### 5.3 技术局限

| 局限 | 说明 |
| --- | --- |
| 版本碎片化 | 每个小版本 `Weixin.dll` 偏移不同，Hook/断点需重新逆向 |
| **零驻留** | **4.1.10+ 稳态内存无任何密钥痕迹，纯扫描不可能成功** |
| 惰性加载 | 部分 DB 仅在访问对应聊天后才打开，可能暂时无法验证 |
| 图片/语音 | 数据库解密 ≠ 媒体解密，图片还需单独的 XOR/AES 密钥 |
| 手机数据 | 手机备份 `Backup.db` 用独立密钥，PC 工具无法解密 |
| 多账号 | 每个 wxid 有独立 passphrase，需分别提取 |
| WAL 文件 | 实时消息可能在 `-wal` 中，需额外处理 WAL 帧解密 |

## 6. 决策建议（针对你的具体情况）

**你已有一个关键优势：passphrase 已经拿到了**（`2da83e8c...dde57b2`，我已验证它跨 10 个
不同 salt 的数据库全部通过 HMAC）。所以：

| 你的需求 | 建议 |
| --- | --- |
| **只是想解密自己的记录** | **什么都不用做**。你已有 passphrase + [standalone_decrypt.py](standalone_decrypt.py)，或直接用已装软件 |
| 长期保存 passphrase | 存进密码管理器。**它跨微信版本有效**，是唯一需要备份的东西 |
| 以后微信升级后还想解密 | passphrase 不变 → 仍可解密；只有**重新登录 + 清缓存**才可能变 |
| 想学会独立取钥（不依赖某软件） | 按性价比：**① wcdb-key-tool（§4，先试）→ ② 降级法（§3.2，最稳）→ ③ wx_key → ④ Frida/x64dbg** |
| 不想冒封号风险 | **只走降级法（方法六）**，零注入 |

**如果以后丢了 passphrase 要重新取：** 推荐顺序
1. `wcdb-key-tool`（管理员 + 已登录，低风险，§4）
2. 降级 4.1.9 提取（最稳，零风险，但要装老版本）
3. `wx_key`（简单但有注入风险）
4. Frida / x64dbg（要自己逆向 RVA，风险最高）

## 7. 我们这一路的实测 vs 文档结论对照

| 我们的观测 | 文档解释 |
| --- | --- |
| 内存中找不到密钥明文（869 MB / 8 种编码 / 3 种内存类型） | ✅ 零驻留策略，4.1.10+ 稳态无痕迹 |
| 上游 YARA stub 4492 次假匹配、0 通过 | ✅ 被动扫描在 4.1.10+ 原理性失效 |
| DLL 22 个候选全部验证失败 | ✅ raw key 缓存已移除，DLL 内部密钥不再是通路 |
| 重登后 `keysUpdatedAt` 未变 | ✅ 密钥与账号绑定，重登不重新派生（除非清缓存） |
| 口令跨 10 个不同 salt 的库全部有效 | ✅ 账号级 passphrase，与文档一致 |
| 解密参数（4096 / 256000 / HMAC-SHA512 / 80 字节保留区） | ✅ 与文档 §1.1 逐项一致 |
| `0xlane/wechat-dump-rs` 返回 451 | ✅ 文档 §7.3：多仓库因 DMCA 下架 |

**结论：我们的实测是正确且完整的，失败不是方法错误，而是撞上了微信的零驻留设计。**
